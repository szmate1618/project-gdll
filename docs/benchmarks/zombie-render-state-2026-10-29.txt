Compact zombie render state and shared idle timing, 2026-10-29
==============================================================

Result
-------
Keep both changes. In the standard healthy 100k case, median CPU render cost
falls 13.178 -> 10.692 -> 9.469 ms (baseline, compact state, plus shared idle
clock), 28.1% lower overall. The mixed case with 100 wounded actors improves
13.219 -> 10.736 -> 9.690 ms, 26.7% lower overall. Images, submitted geometry and
published pose snapshots match. No LOD, animation-rate, precision or GPU-instance
format change is involved.

The corridor case does not establish a render-time gain: 3.157 -> 3.260 ->
3.180 ms, within process variation. Its final candidate update stage increases
about 0.033 ms. In a separate stress fixture updating animation data for every
one of 100000 actors, maintaining the cache costs an extra 0.18..0.21 ms/update
(about 5..6%). This is a real tradeoff, not a universal improvement for every
workload. Server-only simulation does not construct this renderer cache.

Implementation
---------------
Stage A adds a renderer-owned source-ID-indexed ZombieRenderState array. Each
record is 48 bytes on this build, compared with 440 bytes for the authoritative
ZombieInstance. It holds asset/local indices, exact bounds center, locomotion
clock, selected clip, severed index and ragdoll flag. The source gameplay array
remains authoritative and is not moved or replaced. Additional CPU storage is
about 4.8 MB for 100000 actors, plus small per-asset timing constants.

Existing incremental update notifications refresh the cached fields, including
animation-only bounds=false updates. Full refreshes and same-address layer
replacement refresh all records and clip constants. Bounds centers retain the
same float arithmetic and are refreshed with the existing bounds-update path.
Selection preserves original source-ID order and reads cached state/staging;
large gameplay-record accesses remain for camera-pose publication and live
ragdoll palette vectors/revisions. The first stage includes caching clip choice,
clip duration/count and bounds center; its saving cannot be attributed solely
to memory layout.

Stage B computes the shared idle time base once per asset per rendered frame,
then applies each actor's existing phase. Walk/run retain each actor's independent
walkSeconds, and ragdolls retain frame zero. The shared helper and full
animatedFrame use the same canonical operation sequence: double fmod/division/
multiplication, conversion to float, then float phase addition and wrap.
The base remains unwrapped: it can round to frameCount just before a cycle ends,
and wrapping it early changes the final float bits for nonbinary phases.

The original GPU records remain 96 bytes and are still compacted/uploaded for
camera, sun and flashlight independently. FP16 baked animation storage, FP32
world matrices/bone palettes, geometry, wound handling, shadows, 12/35/80 m LOD
thresholds, zoom policy, 5 Hz distant poses and 180 m draw cutoff are unchanged.
No renderer data cache changes authoritative gameplay, simulation cadence or
multiplayer protocol data.

Controls and method
--------------------
Reference revision 3d8ac85 with current Slim1 LOD3. Existing unrelated HUD/map
workspace edits are present in every build. Three full variants are retained:
  baseline  original renderer/animation timing
  compact   cached renderer state, unchanged per-actor animatedFrame calls
  timing    compact plus per-asset shared idle frame base

Each freeze retains executables, static archives, original link objects,
source, shaders and all project src headers. Diagnostic executables compile
against their OWN variant's frozen headers and link only its libraries; compiler
dependencies reject live-header leakage. This avoids mixing private Renderer
layouts after adding cached state. Consumers used in measured executables and executed tests were rebuilt;
no historical mtimes were restored.

Primary comparisons run ABC/CBA in separate processes for each of healthy 100k,
mixed 100k and the actual corridor:18 processes total. Crowd processes use six
rounds of 32 warmup/64 measured frames on a reset deterministic 60 Hz timeline,
384 finite GPU samples/process. Process statistics are medians of six round
means; aggregates are medians of two processes per variant. The crowd stays
idle rather than simulating 100000 active pursuers.

Corridor runs use --fixed-step --frames 240, discard frames 1..60 and retain 180.
Aggregates are medians of two process medians per variant. Sun maps are 1024
square; normal shader/shadow policies are retained. Bird/audio/doodad work and
fog are disabled consistently. No town or zombie assets were regenerated.

Coarse diagnostics run two rounds, 32 warmup/64 measured, one process per variant
and healthy/mixed case (six processes). Stage timers surround measured render
calls. Four whole-population frame/clip hashes per process are collected outside
CPU/GPU timestamps, with per-frame geometry counts and normal captures.
Diagnostics are separate from the primary measurements.

The preparation stress control runs baseline/final/final/baseline: four processes,
each with eight 128-frame rounds for both visible and hidden views (2048 timed
updates/process). Every actor receives changing walk/run time and an animation-only
notification. Renderer::updateZombies alone is measured; rendering, caller edits
and diagnostic glFinish are outside that timer. It quantifies cache maintenance,
not end-to-end moving-crowd rendering.

Hardware: Radeon 660M, radeonsi/LLVM 19.1.1, Linux 6.11.0-29. Idle/competing-work
guards and telemetry precede each process. GPU queries stay asynchronous; no
builds, other GPU experiments or timing analyses run during measurements.
Presentation/VSync is outside the timers. CPU render can include driver stalls;
CPU/GPU overlap, so do not add columns or translate them directly to FPS.

This fixture deliberately forces 100000 updates every step. It preserves the
same published poses and counts. The added work is the price of keeping the
render cache current; these measurements do not establish the full-frame result
for 100000 moving pursuers. The large overview savings above are for stationary
animated actors whose preparation is unchanged between frames.

Correctness and verification
-----------------------------
All primary screenshots, metadata and final geometry counts match across variants.
Diagnostics additionally match per-frame counts and all 100000 published frame/clip
snapshots at all four sampled points. Preparation control pose checksums and
captures match. Every recorded frame has finite CPU/GPU measurements.
Healthy stays 100000 actors/10 draws/6,000,000 triangles, all LOD3; mixed stays
100 LOD0 wounded+99900 LOD3 healthy, 30 draws/6,184,100 triangles. Corridor final
counts stay 107/53000 visible, 20 draws, LOD0/1/2/3=0/0/25/82, 13,809 camera and 7200
sun triangles, with unchanged town/tree/forest/group-rejection counters.

Fresh builds succeed for viewer/client, standard crowd/preparation benchmarks,
animated-model/LOD/render-update/FP16 tests and zombie/shadow rendering tests.
Four focused CPU CTests pass: animated_model,zombie_lod,zombie_render_updates,
zombie_animation_buffer. Three gameplay CTests pass: zombie_shooting,
zombie_hit_capsules,zombie_transition. Hardware zombie_renderer/shadow_renderer
pass for both compact and final variants. The final authored-asset GPU test
also passes all ten idle/walk/run rigs and live ragdolls.

Regressions cover bounds=false clip/time/phase changes, camera-only reentry
after hidden updates, advancing idle time without source notifications, missed
consumers and layer replacement at the same address. Twelve independent frame
bit goldens cover shared/full timing, early-wrap rounding, exact wrap, nonbinary
phases, very large time, negative/nonfinite time and out-of-cycle phases, plus
invalid timing validation. Ten golden frame outputs were first checked against
the frozen baseline library; the other two have exact closed-form results.

Across 28 benchmark processes, recorded RAM availability stays above 16.68 GiB;
no swap-out or memory-pressure stalls occur. Primary runs read nine swap pages
(36 KiB) system-wide; preparation/diagnostics read none. Sampled GPU temperatures
span 46..64 C. Clocks remain automatic and are not normalized. All 259 recorded
asset/map/scenario fingerprints and frozen variant inputs remain unchanged.
Unrelated existing worktree changes were preserved.
