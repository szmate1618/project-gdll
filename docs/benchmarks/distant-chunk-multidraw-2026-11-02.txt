Batch the distant-cache chunk submissions — 2026-11-02

Scope
-----
Base revision: ff7911a on master (the distant-cache implementation).
This follow-up batches the new terrain/road/railway/fence chunk path only. The
normal large-mesh draws and existing forest/building batching remain intact.

drawStaticChunks now collects the same selected index ranges in their original
order and submits one glMultiDrawElements per source mesh and pass. Counts and
byte offsets use reusable Renderer-owned CPU arrays, reserved at preparation.
The source VAO element binding is restored after submission. Empty selections
issue no draw. The caller counts one GL API submission, consistently with
forest multi-draw batches; the geometry ranges are unchanged.

Result
------
This closes the submission-batching omission introduced by the cache. It
substantially reduces GL API calls and improves some timings, particularly
stationary town. It does not show a uniform p95 improvement across all motions.
The pooled stationary overview is slightly slower; town walk-turn CPU p95 also
increases slightly. Stationary overview GPU p95 rose 0.103 ms (1.9%) and CPU
p95 rose 0.161 ms (3.3%). These increases have not been established as noise.
Keep these mixed timing results visible rather than
interpreting fewer API calls as a guaranteed frame-time improvement.

Method
------
AMD Radeon 660M, OpenGL 4.6 Core, Mesa 24.2.8-1ubuntu1~24.10.1, 1280x720.
Same map, trees, forest patches, camera file, shaders, shadows, LoD and 15 Hz
capture policy. Saved pre-fix executables contain matching compiled layouts;
no historical object is linked against changed class headers.

Overview and town each use static, 1.5 m/s + 40 degrees/s walk-turn, and
180 degrees/s fast-turn. Each binary alternates normal/cached rounds. Initial
order: before overview, after overview, after town, before town. A reversed
order repeat checked the initially mixed timings: after overview, before
overview, before town, after town. Each block has 3 rounds, 32 warmup and 128
measured frames per mode. Combined: 6 rounds / 768 samples per case and mode.
Camera and refresh clocks advance exactly 1/60 second per frame.

Timestamps are asynchronous, max four frames in flight. Waits, captures and
query collection stay outside measured CPU render sections. No AI, audio,
physics steps, HUD or presentation in map cases. Builds/tests/benchmarks ran
sequentially. No other running game/benchmark process was found before timing.
GPU power/clocks were not pinned; separate normal controls are retained to
show run variation. All measured GPU samples are present.

Validation and remaining limits
-------------------------------
Full default build, benchmark targets, viewer and client rebuilt successfully.
Five focused GPU regressions passed: distant scenery, native presentation,
building rendering, tree billboards and forest visibility. Existing tests
exercise multiple nonzero index offsets, near/far filtering and toggling back
to original index lists.

The after build also ran all eight map views and all three motions, one round
of 64 frames per mode. Automated byte comparisons match all 24 paired-view
captures from the initial/reversed runs, all 48 broad captures against the
previous single-rectangle build, and the crowd control capture: 73 pairs total.
Manual visual review remains with the user.

The standard 100,000-zombie before/after control uses six rounds of 32 warmup
and 64 measured frames, caching requested but inactive in both. Every measured
frame retains 100,000 living instances, 10 draws and 6,000,000 camera triangles.
  GPU p95:        9.483 -> 10.775 ms
  CPU render p95: 13.051 -> 13.818 ms
  GPU average:    7.387 -> 6.821 ms
  CPU average:    10.399 -> 10.101 ms
The chunk submission path does not execute in this control. Its differing tails
illustrate timing variation that these runs do not isolate or explain. They
are not evidence of a chunk-batching gain in the crowd case.
