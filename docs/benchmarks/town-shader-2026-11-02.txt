Static town shader variant — 2026-11-02
=======================================

Implementation
--------------
Town camera geometry uses a third linked basic shader variant, compiled during
Renderer construction with TOWN_GEOMETRY=1 and ZOMBIE_WOUNDS=0. It removes baked
animation/interpolation, live skinning, instance transforms, tree billboards,
canopy varyings and zombie wound/cavity handling. The full and wound-free
animated variants retain their original behavior. Shared lighting/material
calculations stay in basic.vert/basic.frag rather than duplicated shader files.

The variant draws both opaque town sources/batches and sorted town glass.
Moving doors retain their ordinary object transforms. Materials, alpha masks,
double-sided handling, fog, lighting, forest-range clipping and depth conventions
are preserved. Shadow casters, vegetation, actors and ordinary runtime props
retain their existing programs. Program switches select matching cached uniform
locations and invalidate the material cache. Camera lighting/matrices are
prepared even for a scene containing only transparent town geometry. Scenes
with no eligible town sources skip that preparation. The shader adds no meshes,
textures, per-object options or public runtime selection switch.

Correctness
-----------
The full CMake build succeeded. All 24 registered graphics/weapon-overlay
regressions passed on the AMD Radeon 660M, plus viewer_model_visibility.
The existing unused debugMessage warning remains. The added building regression
checks independently expected glass colors under changing ambient illumination
with no opaque sources, including repeat rendering and all supported depth modes.
Existing checks cover doors, texture restoration between renderers, reflected
roof geometry, masks, glass ordering, vegetation and healthy/wounded actors.

Initial measurements: power-source confound
------------------------------------------
The initial four-process ABBA map/crowd comparison, a reverse-order crowd repeat
and an in-process crowd diagnostic were completed before the user reported
disconnecting the laptop charger. AC power was not recorded continuously during
those runs; checking AC afterward cannot establish the state during measurement.
Their timing estimates are withdrawn and must not support a speedup or regression
claim. This includes the preliminary 5% daytime-town GPU saving discussed in chat.
Their matching images/counts remain useful correctness evidence.

The initial crowd intervals varied materially across processes. Alternating
paths in one renderer did not reproduce its separate-process CPU slowdown, but
that diagnostic also lacks continuous power provenance and is not a final result.
No power profile, clock limit or system setting was changed by this work.

Final comparison protocol
-------------------------
Frozen baseline: clean revision 1090b38 before this change, freshly rebuilt.
Frozen candidate: the implemented variant and matching rebuilt Renderer users.
Both use the current headers/libraries in their own builds; saved executables
and shader directories remain separate. No historical headers or ABI layouts
are mixed. No generation, configuration, map, asset or player-save changes occur.

The user selected charger-connected benchmarking. The replacement comparison
requires AC online and the existing balanced platform profile before every
process. A common monitor records AC, profile and available GPU clock/activity
readings every 0.5 seconds; any observed AC/profile change invalidates the run.
Sampling cannot establish perfectly constant clocks or exclude other workloads.

Each map process runs all 13 standard benchmark_render_wins views at 1280x720,
with six rounds of 60 warmup and 64 measured frames per view. Each standard
100,000-zombie process has six rounds of 32 warmup and 64 measured frames.
Process order is baseline/candidate/candidate/baseline separately for map/crowd.
Each process result is the median of six round means; aggregate levels are the
median of the two process results per version, without pooling frames.
Asynchronous GPU timestamps and bounded in-flight work are retained. Warmup
completion, query draining and captures are outside CPU render timing. CPU and
GPU overlap; elapsed intervals include stalls and are not presented gameplay FPS.
Map cameras are static; animation input follows deterministic 60 Hz, with no AI,
audio, player updates, dynamic physics or presentation. Crowd uses its standard
deterministic idle simulation/preparation and verifies all 100,000 submissions.

The AC comparison favors the first town variant in the tested town views, with
the sparse-scene CPU cost and variation limits above. The battery comparison
below does not reproduce that daytime-town gain. Further specializations need
their own matched measurements. No general gameplay/FPS claim follows from
these static views or from timing the entire GPU interval.

-------------------

against the AC comparison before running. No rebuild or source change was made.
run_battery.py repeats the same map/crowd ABBA order, cameras, dimensions,
warmups, frames and aggregation. It requires AC offline, balanced profile and
discharging battery; these values and battery capacity are sampled every 0.5 s.
All 634 samples retain those conditions. Recorded capacity spans 91% to 86%.

The daytime-town shader gain does not repeat on battery: CPU render is 0.086 ms
higher (1.9%) and GPU elapsed is 0.153 ms higher (3.7%). In execution order,
CPU values are 4.227 / 4.578 / 4.529 / 4.708 ms; GPU values are
3.939 / 4.129 / 4.311 / 4.197 ms. Adjacent CPU comparisons have opposite signs;
both baseline endpoints and several other views vary materially. These results
do not establish a repeatable CPU regression or a general optimization benefit.
Nighttime-town results are mixed: driving GPU improves 4.7%, flashlight-off
improves 2.0%, flashlight-on is 3.0% slower. Forest/clearing GPU changes favor
the variant in this session, while CPU results vary by view.

Comparing the current variant across power states, daytime-town CPU render is
4.004 ms AC versus 4.553 ms battery (+13.7%), and GPU elapsed is
3.619 versus 4.220 ms (+16.6%). The standard crowd behaves differently:
CPU render is 10.273 versus 13.226 ms (+28.7%), while GPU elapsed is
6.908 versus 5.300 ms (-23.3%). A shorter GPU interval is not automatically a
faster completed frame. Crowd completed-frame timing (including idle simulation,
preparation, render submission, query scheduling and final GPU drain) is
10.693 ms AC versus 13.725 ms battery (+28.4%) for the current variant.
This remains offscreen benchmark throughput, not presentation/gameplay FPS.

Both power-state comparisons use the identical frozen workload, but they were
run in separate sessions with unlocked clocks and potentially different thermal
or background conditions. The results show power-state-dependent measurements;
they do not isolate unplugging as the sole cause of every difference. The earlier
13% town improvement must not be presented as a power-independent gain. Retain
both comparisons and the mixed battery result when judging this optimization.
