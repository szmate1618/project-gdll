CPU-load-dependent GPU elapsed time: controlled scenario investigation
Recorded 2026-10-22; measured source revision bb0f7fb.

Finding and scope
Heavy CPU work increased GPU elapsed time for the same rendered scene on an AMD
Radeon 660M integrated GPU. Independent GPU timestamps confirmed the effect;
unchanged draw counts and pixel-identical final captures excluded additional
visible geometry as the explanation for these controlled runs. Freezing scenario
movement removed most of the increase. Artificial CPU computation reproduced
much of it with movement still frozen; sleeping for the same duration did not.

This establishes a CPU-load-dependent rendering slowdown on the tested system.
It does not isolate a driver defect or prove a specific power-management cause.
Shared CPU/GPU power and clock behavior is a likely contributor; effects from
driver scheduling and shared memory were not separated. Do not generalize these
numbers to all integrated GPUs, discrete GPUs, drivers or power profiles.

Hardware and method
- AMD Radeon 660M, radeonsi/rembrandt, LLVM 19.1.1, DRM 3.61.
- Mesa 24.2.8-1ubuntu1~24.10.1, OpenGL 4.6 Core, Linux 6.11.0-29-generic.
- Existing local map/assets and scenarios/test-horde/scenario.toml: 1,600 actors.
- Hardware rendering, sequential runs, hidden 1280x720 window, audio disabled.
- Frozen lighting at hour 12.3; normal render settings and zombie LOD retained.
- Fixed street camera for this map only: spawn X=-526.465, Z=296.095 meters;
  yaw=-90, pitch=0. Do not reuse these coordinates blindly for another map/frame.
- Each case: 480 frames, discard the first 60; report the remaining 420 frames.
- Whole-frame GL_TIME_ELAPSED plus independent GL_TIMESTAMP pairs and per-pass
  timestamps, collected asynchronously. End-of-run draining outside measurements.
- One run per control, not repeated alternating rounds or a portable threshold.
- GPU clock states sampled read-only every 100 ms. Hardware settings unchanged.

trees and fences, rather than only a foreground wall.

Interpretation for future agents
1. GPU elapsed queries measure time between command-completion points, including
   intervening stalls. They are not active-GPU-utilization or instruction counts.
   The observed increase is real elapsed time; agreement between independent
   query methods does not identify its hardware cause.
2. The increase spans town, vegetation and shadow passes. It cannot be assigned
   to zombie vertex animation from the population count or GPU headline alone.
3. Frequent sampled clock states of 200-533 MHz accompanied scenario/CPU-load
   runs; the frozen fast-rendering control reached 1,899 MHz more frequently.
   Samples include idle periods and cannot establish clocks during each draw,
   prove thermal throttling, or isolate shared power limits.
4. Freezing movement preserves population/assets but changes the CPU workload.
   Rendering-only benchmarks cannot predict full gameplay cost on this system.
   Conversely, reducing CPU work can improve GPU timings indirectly without a
   shader or geometry change. Hold simulation workload and overlap comparable.
5. Do not subtract CPU simulation time from the GPU query result, sum CPU and
   GPU times for frame duration, or add production glFinish calls as a remedy.
   Serialization changes overlap, scheduling and clocks; its faster GPU number
   alone does not establish better end-to-end FPS.
6. Investigate GPU regressions with matched camera, lighting, render counts,
   simulation workload and hardware state, then compare frozen, CPU-busy, sleep
   and serialized controls if needed. Repeat paired rounds for optimization
   claims; retain normal-overlap end-to-end frame/FPS measurements separately.

Animation and profiler semantics
Normal clips use pre-baked per-frame vertex positions/normals in GPU texture
buffers. shaders/basic.vert selects/interpolates them during camera/shadow draws.
Actors culled from all passes incur no vertex animation. Ragdolls have a separate
live-skinning path. CPU movement, collision, clip selection and animation clocks
remain CPU work; GPU animation does not imply GPU navigation or behavior.

The behavior timer includes scenario travel. The old "active zombies" counter
counted nearby behavior-pool entries, not route followers; the current label is
"behavior pool entries". Scenario routes continue outside activation range and
camera visibility. "Incremental" render preparation can still update nearly all
actors. Initial paths are preplanned at scenario load in this source revision;
their per-frame following and movement checks still cost CPU time.

Reproduction and retained local evidence
The investigation used scratch copies of viewer sources linked against existing
CMake libraries; it did not change production code or replace godollo_viewer.
These diagnostic executables, environment switches and scripts are NOT tracked
benchmark APIs and may be absent in another checkout. The tables and protocol
in this report remain usable when those ignored artifacts are unavailable.

To recreate the experiment on another checkout, instrument a focused harness:
- Load one identical scenario, scene and fixed camera for all cases. Freeze only
  updateBehavior for frozen controls, retaining assets, normal rendering and
  physical scene setup. Record actual draw/triangle counts and captures.
- Compare normal updates, frozen updates, frozen plus 25 ms scalar computation,
  frozen plus 25 ms sleep, and normal updates plus completion after rendering.
- Place artificial work outside render timers. Retain asynchronous whole-frame
  and per-pass GPU timestamps; record CPU render/simulation separately. Keep the
  optional completion wait outside timed rendering and report its FPS impact.
- Use 480 frames per case, discard 60, compare the remaining 420. Save GPU/driver,
  assets/settings, camera, power state and source revision with each new run.
- Select the actual GPU device for optional read-only clock monitoring; do not
  assume the original machine's sysfs card number exists on another system.
- Preserve the configured map, assets and hardware settings. Keep raw output in
  ignored build/benchmarks/ directories. Use useful captures and repeat rounds
  before making an optimization claim.
