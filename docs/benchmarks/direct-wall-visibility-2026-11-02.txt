Direct camera selection of distant wall batches — 2026-11-02
===========================================================

Question and scope
------------------
Can the retained 128 m roof-batch camera path be extended to simple wall batches
and their detailed alternatives to reduce source selection, detail filtering,
classification and sorting? Static GPU geometry, the town shader, shadow queries,
material behavior, collision and map data remain unchanged. No 512 m parents.

The trial replaces RoofVisibility with one BuildingVisibility camera BVH containing
roof batches, wall batches and remaining singleton sources. Each wall batch also
owns high-detail alternatives whose named group and full source transform identify
one unambiguous simple-wall batch. Groups split across multiple wall batches keep
their detailed alternatives source-selected. Zero-distance surfaces are never
suppressed as detail alternatives. Bounds include complete transformed geometry
and moving-panel padding, not nominal tile boxes.

If every building in a selected wall batch is beyond the existing conservative
batch detail bounds/range (including scope magnification), the query skips detailed
alternatives and emits the minimum visible simple-wall source ID. A fully contained
batch avoids per-member tests. Boundary batches test simple members to preserve
exact source counts and batch activation/order. Near batches or disabled batching
expand original sources; the original per-building detail filter still selects
the correct alternatives. Separate caller-owned coarse scratch allows expansion
without overwriting unread query entries. Non-roof/wall sources remain individual.

Protocol declared before wall timing
-----------------------------------
Primary: same completed-frame in-process control used for the roof trial: four
base/inverse/inverse/base processes, 8 blocks/view, 60 warmup and 512 measured
frames/block, three views (town, flashlight town, old forest 100 m). No CPU phase
clocks or GPU timestamps in primary rendering; final GPU retirement is included.
Each process takes the median of four adjacent baseline-minus-candidate block
pairs. Aggregate saving is the median of those four process medians. Percentage
divides paired saving by the independent baseline flat level. A clear gain needs
>=1%, all four process medians positive, >=12/16 positive pairs; clear regression
is symmetric. Otherwise mixed. This is a practical rule, not a significance test.

The baseline query is the frozen roof-only implementation, not a full source query
or the new implementation with a switch that expands all wall batches. Both camera
indexes remain allocated inside the control context; their construction is outside
measurement. The control links against matching current Renderer headers and libs,
with the original roof module compiled separately and no duplicate renderer object.
Accepted roof-only normal benchmark executables are frozen as broader controls.

Two separate diagnostic processes use the base/inverse orders and 128 measured
frames/block, CPU stage clocks, asynchronous whole/opaque/glass timestamps (maximum
four frames in flight), selected-list and bounds-test counters. These diagnostic
intervals do not determine the primary throughput decision.

AC online and balanced profile are required and sampled every 0.5 s. The same
published map, tree/forest placements, cameras, resolution, depth/shadow settings
and frozen shader files are used in both paths. Capture/count equivalence is
required. No concurrent build/benchmark or map generation. Primary has no gameplay AI/audio,
physics movement or presentation wait; this is a rendering experiment. Clocks,
temperature and background activity remain unlocked. Battery remains unmeasured
for walls; the separate roof AC follow-up is mixed.

Broad controls: all 13 standard map views (3 x 64 samples after 60 warmup frames)
and the real-asset 100,000-zombie open-area case (6 x 64 samples). Byte-identical
captures, settings, input cameras and geometry counters are required; /usr/bin/time
records peak process RSS without interpreting a single process pair as a precise
index-allocation or throughput comparison.

Completed-frame results and decision
------------------------------------
Retain direct distant-wall selection. The flashlight-town result meets the
predeclared practical rule in every process and all 16 pairs. Daytime has only
10/16 faster pairs and is mixed despite positive per-process medians. Forest
has a small slowdown (about 0.020 ms / 0.34%) below the 1% practical threshold;
all four process medians are negative and only 4/16 pairs are faster. This is
not an equivalence result, and no universal speedup is claimed.
