Town shader and direct building visibility: master integration, 2026-11-02

Baseline: master 48de753e23bf9049e620312ca7bf5cce353b63d6.
Candidate: ports of 9ceea1a (town shader specialization) and a2177f1 (direct
roof/wall visibility), adapted to the current distant-scene rectangle cache.
This measures the combined port, without isolating each feature's contribution.
The separate experimental CPU building occlusion and pixel-LOD trials are absent.

Integration
===========
Town camera draws use a static shader compiled during renderer construction.
The camera queries complete roof/wall batches and remaining source bounds;
near wall batches expand to their original detailed sources. Shadow queries
retain the original source BVH. Geometry, collision, generated map files,
network data and the minimum OpenGL 3.3 requirement are unchanged.

The current master cache requires additional integration beyond the old commits:
- Prepare the town program's lighting, samplers and matrices before far capture,
  including scenes containing only glass.
- Restore the full program and camera matrices before instanced vegetation in
  both far capture and foreground passes.
- Classify cache candidates with whole-batch bounds rather than the selected
  representative's bounds. A batch touching the near region cannot activate
  an otherwise empty far capture.
- Preserve exact visible-source counts when the list contains batch representatives.
The existing multi-draw chunk path and reversed-depth handling are retained.

===========================
Baseline executables, libraries, sources, headers and shaders were frozen before
source mutation. The matched baseline harness links saved 48de753 libraries
against matching headers; the candidate links successfully rebuilt current
libraries and headers. Compiler dependency files and linker maps verify the
layouts. No historical object uses the changed Renderer class layout.

AMD Radeon 660M (radeonsi, rembrandt, LLVM 19.1.1, DRM 3.61,
Linux 6.11.0-29-generic); OpenGL 4.6 Core, Mesa 24.2.8-1ubuntu1~24.10.1.
Release -O3, 1280x720; identical reversed FP32 depth and shadow/LoD settings.
The user closed Firefox and confirmed readiness after all builds and tests.
Sixteen processes ran sequentially from 16:30:58 to 16:35:23 Europe/Budapest.
All 32 before/after power snapshots show AC online=1 and balanced, via sysfs
and powerprofilesctl. Clocks and temperature were not pinned or measured.
There were no overlapping builds, tests or other benchmark runs.

Primary completed-render throughput
===================================
Four static views: daytime town, unrestricted old forest, flashlight town,
and nighttime driving with flashlight shadows configured. In driving mode,
vehicle occupancy suppresses the held flashlight and retains headlights.
Cache disabled and enabled are compared separately. Process order is ABBA
(baseline/candidate/candidate/baseline) with cache off and BAAB with cache on.
Each process uses 2 rounds per view, with 60 warmup and 256 measured frames per
block: 16,384 measured frames in 64 completed blocks across eight processes.

Timed blocks contain no per-frame CPU clocks, GPU timestamps, event polling or
output writes. They include render + glFlush and final GPU retirement. Loading,
warmup and captures are excluded. Animation and presentation/cache clocks
advance by an explicit 1/60 second per frame in BOTH variants, preventing a
faster renderer from doing fewer cache refreshes. No simulation steps occur.

=================================
Standard open-area control, frozen baseline/candidate executables and matching
shader directories, ABBA process order. Six rounds per process, 32 warmup and
64 measured frames per round: 1,536 measured GPU/CPU samples, all present.
All runs retain 100,000 visible actors, 10 draws and 6,000,000 camera triangles.
This control uses the standard instrumented harness, separate from the primary.

Completed render cost: 10.7383 -> 9.9528 ms (-7.31%).
GPU mean: 7.6996 -> 7.0413 ms; GPU p95: 11.2164 -> 8.7894 ms.
CPU mean: 10.3369 -> 9.5707 ms; CPU p95: 13.9996 -> 11.8846 ms.
Per-process completed costs: baseline 11.1280 / 10.3485 ms;

Baseline process range is 7.53%, candidate range 2.95%. This mostly exercises

It shows no observed crowd regression under this protocol, with residual
process variation despite the unchanged AC/profile settings.

Correctness and limits
======================
All 56 paired recorded geometry/source/cache-counter rows match exactly;
camera and runtime settings match. Cache is active in every requested cache-on
view. All 24 map baseline/candidate image pairs and 3 additional crowd pairs
are pixel-identical. Visual inspection includes useful town buildings, foliage,
flashlight and headlights; there are no benchmark GL errors. All 16 processes
exit successfully. No missing geometry accounts for the timing improvement.

Before timing, full rebuild succeeded; 8 focused CPU tests and 24 graphics tests
passed without skips. Regressions cover representative ordering, range/scope
boundaries, transformed bounds, near facade fallback, source counts, lighting
changes, and restoring instanced vegetation in cached and foreground passes.
After timing, the two building/cache renderer tests also passed with
MESA_GL_VERSION_OVERRIDE=3.3, MESA_GLSL_VERSION_OVERRIDE=330 and
MESA_EXTENSION_OVERRIDE=-GL_ARB_clip_control, exercising the conventional-depth
fallback. No additional performance runs were made for that check.

No steady-rendering regression was observed in this matrix. Results apply to
this AC-powered Linux GPU and these static render workloads. Full-game CPU
simulation, AI, dynamic physics, audio, networking, VSync/input latency, Windows,
battery operation and other GPUs were not benchmarked. Earlier individual
feature reports have mixed results on other power/workload combinations.
The combined gains here do not replace those limits or prove a gain everywhere.

The new shader program and CPU spatial index add loading-time work and storage.
Startup time, index-allocation time and RSS were not measured separately.
Whole-process wall times include loading, warmup, captures and timing; they are
not startup measurements. No map regeneration is required.
