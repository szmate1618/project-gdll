Opaque town source-ID radix ordering — 2026-10-29
================================================

Result: keep the opaque sorter change
------------------------------------
This experiment replaces comparison sorting of larger opaque town result lists
with byte radix sorting, while retaining ascending source IDs. The actual-map
town sort phase falls from 0.462395 to 0.077541 ms/frame (83.2%). Primary town
CPU render falls from 4.989 to 4.557 ms (8.7%), with savings in both ABBA pairs.
Town GPU elapsed is effectively unchanged, 4.487 -> 4.513 ms. The standard
100k empty-town control is unchanged: CPU 16.985 -> 17.006 ms (+0.12%).
Keep the CPU optimization; these results do not establish a general GPU gain.
Nighttime-town GPU intervals increase in both repetitions, as detailed below.

Implementation
--------------
Baseline revision: e4e2f979560a30da0dc1a6909ea5da49f1aacba9, with common opt-in
sort instrumentation added before building both versions. The baseline keeps
std::sort; the candidate uses it for at most 256 opaque IDs and otherwise uses
stable least-significant-byte radix passes with 256 counting buckets. The
significant-byte bound comes from the fixed scene population, preserving full
size_t IDs even when few results contain high source indices.

Renderer owns and reuses an O(opaque-result-count) scratch vector for its fixed
scene lifetime. This adds RAM proportional to the largest opaque list rendered.
Ascending source order is preserved for opaque surfaces, including coplanar
overlaps. Transparent back-to-front order and equal-depth source ties retain
their existing comparison sort. Visibility membership, material handling,
building batching, shadows and zombie ordering are unchanged. No runtime sorter
selection option is introduced.

The new coarse Stage::townSort surrounds only opaque source-ID sorting in the
real gatherVisibleSceneDraws path. benchmark_render_wins accepts an optional
trailing --profile after all positional arguments. It captures measured render
frames only and writes opaque-sort-stages.csv with view, round, frames,
opaque_sort_ms (mean ms/frame) and sort_calls (raw measured calls). Both timed
versions use this same harness and instrumentation. Primary runs leave capture
disabled; phase-enabled diagnostics are evaluated separately.

Build isolation and correctness
-------------------------------
Baseline/candidate executables, sources and shaders were frozen separately.
The added scratch member changes Renderer layout, so every measured consumer
and all six focused test binaries were successfully rebuilt for the candidate.
No old/new Renderer layouts are mixed. No map or asset generation was run.

The model-visibility CPU suite passed 1/1. Hardware GPU suites passed 5/5:
roof, wall, zombie, shadow and building rendering. The new building regression
uses independent pixel expectations for coplanar opaque ownership across
255/256 and 65,535/65,536 source IDs, glass depth order and equal-depth ties.
It also checks culling on/off, small and large result lists, repeated rendering
and scratch reuse. Large fixtures retain high IDs without thousands of GPU
draws by excluding distant shared-quad fillers through existing detail range.

Primary protocol
----------------
Four standard 100k-crowd processes run comparison/radix/radix/comparison (ABBA).
Each has six rounds of 32 warmup and 64 measured frames with the standard
deterministic 60 Hz simulation/animation timeline. The required workload has
100,000 LOD3 actors, ten camera draws, 12,580,000 camera triangles and zero
zombie sun casters. This synthetic empty-town control measures shared-renderer
regressions; it is not evidence of a town-sort benefit.

Four all-view map processes then run their own ABBA. Each of the 13 views uses
six rounds of 48 fenced warmup and 64 measured frames. Cameras/maps are static;
animation input follows deterministic 60 Hz without AI, audio, player updates,
dynamic physics or presentation. Warmup fence completion and bounded async GPU
query waits remain outside CPU rendering timers. No coarse stage capture runs
in the primary comparison.

The tracked summarizer takes each process's median of six round means per
view; cross-process aggregation takes the median of two process results per
version. Frame rows are not pooled across independent processes. Each primary
view/process must retain 384 finite GPU samples. Counts, view metadata, input
fingerprints and per-view captures are checked independently. Map metadata
comparison ignores only the intentionally different saved shader-directory path.

Actual-sort diagnostic protocol
-------------------------------
Two additional processes, comparison then radix, use the same map harness with
--profile and only sort-town/sort-aerial. Each view has six rounds of 48 fenced
warmup and 64 measured frames. Each sort-phase mean must contain exactly 64
calls. Report medians of six round means for each view/version. These are
single-process diagnostic controls, not additional primary timing repetitions.
They measure the actual renderer's sort phase, rather than a generic synthetic
100k integer sort. Final captures and geometry counts must match independently.

Host controls and timing limits
-------------------------------
The runner refuses to overwrite retained outputs and guards against known
competing benchmarks/builds and heavy LoD preparation. Before every invocation
it waits five seconds, then requires three zero-GPU samples 0.5 seconds apart.
Read-only telemetry samples activity/clocks, temperature, available RAM, swap,
GTT and memory pressure every 0.5 seconds. Clock and power settings are not
locked. These checks cannot remove all scheduling or integrated-GPU variation.

GPU timestamps bracket renderer.render and may include CPU submission gaps.
A changed whole-render interval does not by itself establish a corresponding
change in GPU shader execution. Small full-frame differences need comparison
with process variation and the independently captured opaque-sort phase.

beats every baseline. The separate sort-phase result supports the CPU saving
without assigning the full render difference to a single tightly controlled

small movement lies within its baseline process spread and is not a town gain.

Old-forest-100m and aerial each have seven visible town sources and execute the
same small-list comparison sort in both versions. Their CPU movements cannot
be direct radix work savings or costs. The old-forest-100m 0.043 ms increase,
with GPU unchanged around 6.32 ms, illustrates whole-render variation or other
indirect effects that this experiment does not isolate.

Nighttime GPU movements are mixed: forest intervals decrease, while town off/
on/driving increase by 6.1%/6.5%/2.9%. In each nighttime-town view both radix
GPU process medians exceed both comparison medians; these increases should not
be dismissed as proven noise. Unlocked clocks and whole-render timestamps do
not distinguish GPU execution from scheduling/submission effects. No general
GPU performance improvement or equivalence is claimed from this session.
