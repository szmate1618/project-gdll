Zombie visibility radix ordering — 2026-10-29
============================================

Result: keep radix ordering
---------------------------
Replacing comparison sorting with byte radix ordering for larger result lists
reduces the isolated dense-100k query from 3.188820 to 1.194211 ms (62.6%),
while preserving exactly the original ascending source IDs and pass masks.
The complete 100k render also improves in both matched process pairs.

Median of two process results per version, milliseconds:

Workload                 CPU render comparison -> radix    GPU elapsed
100k open crowd                    19.609 -> 16.919        15.178 -> 13.323
Gray-Scott corridors                3.630 ->  3.231         4.668 ->  4.194

Crowd savings are 2.691 ms CPU render (13.7%) and 1.855 ms whole-render GPU
elapsed (12.2%). Both radix processes beat both comparison processes for both
timers. Corridor CPU render is 11.0% lower, but simulation also shifts from
2.575 to 2.271 ms; its broader host variation prevents attributing that entire
gain to radix ordering. These are results on one integrated GPU/driver system.

Implementation
--------------
Baseline revision: 5fc39cf4fa1ff121fd11b3a4064f68c78a4ba1d0, using std::sort.
The candidate keeps comparison sorting for at most 256 visible results. Larger
lists use stable least-significant-byte radix passes with 256 counting buckets,
copying each result's ID and independent camera/sun/flashlight flags together.
Pass count derives from the population's maximum possible size_t ID rather
than visible count; 100,000 actors need three bytes. IDs are not narrowed.

The index owns and reuses an O(visible-count) scratch vector. reset releases
its capacity when replacing a population. This adds scratch RAM proportional
to the largest result list since reset. No runtime selection option or new
caller responsibility is added. The API explicitly retains ascending unique
IDs independent of traversal history. Culling, bounds refitting, grouping,
LOD policy, renderer selection and shaders retain their existing behavior.

This preserves the ordering that the preceding no-sort experiment found useful
for consumer locality; see zombie-visibility-no-sort-2026-10-29.txt. That failed
experiment removed ordering entirely and is a separate control, not this
candidate's baseline.

Build isolation and validation
------------------------------
Before editing, baseline binaries, shaders and relevant sources were saved.
The scratch member changes class layout, so all measured consumers were rebuilt
for the candidate. No historical and current class layouts are mixed. Both
versions use the unchanged benchmark harness and the normal Release build.
No assets or map outputs were regenerated. An initial executable-mode setup
failure occurred before a timed invocation; its log is retained separately.

After the successful candidate build, focused CPU suites passed 5/5: visibility,
visibility refit, zombie LOD, zombie render updates and zombie visibility. GPU
suites passed 2/2: zombie renderer and shadow renderer. The new regression uses
an independent full-population oracle for exact ordered IDs and all pass masks.
It covers shuffled insertion, sparse high IDs, 255/256 and 65,535/65,536 digit
boundaries, 256/257 result thresholds, camera/light unions, empty/small results
following large results, erase/reinsert and reset after pending removal work.

Full-render protocol
--------------------
Radeon 660M, radeonsi/rembrandt, LLVM 19.1.1, DRM 3.61, Linux 6.11.0-29-generic,
Mesa 24.2.8-1ubuntu1~24.10.1. The standard ten-asset 100k overview uses 1280x720,
sun map 1024, all LOD3,
10 camera draws and 12,580,000 camera triangles, with zero zombie sun casters.
Each of four ABBA processes uses six rounds of 32 warmup and 64 measured frames
at deterministic 60 Hz. Aggregate the median of six round means per process,
then the median of two process results per version.

The generated map with gray-scott-corridors uses --fixed-step --frames 240,
no audio/doodads/birds, no haze/ground fog and a frozen day clock. Discard the
first 60 chronological frames, then take each process's median of frames
61..240; aggregate the two process results per version. It has its own ABBA.

Runners guard against known competing builds/benchmarks, wait five seconds
and then require three zero-GPU samples 0.5 seconds apart. Telemetry samples
clock/activity, temperature, RAM, swap, GTT and memory pressure every 0.5 seconds.
An independent LoD capture completed before CPU timing began. GPU timing
starts only after the host guard is quiet. No clock/power setting is locked.

All eight invocations completed successfully. Crowd has 384 finite GPU samples

FrameProfile's GPU timestamps bracket renderer.render, including CPU visibility
and instance preparation before draw submission. The interval can include GPU
idle time waiting for CPU submission. A lower interval does not establish a
corresponding reduction in GPU shader execution time. The CPU query reduction,
preserved ordering and full crowd CPU-render result support keeping this change.
