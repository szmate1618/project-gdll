Town shader: alternating paths in one renderer — 2026-11-02
==========================================================

Purpose
-------
The preceding town-shader-2026-11-02.txt separate-process comparisons favored the
specialized town shader on AC but not on battery. This control alternates paths
inside one Renderer and GPU context, measures completed frames separately from
phase instrumentation, and isolates town preparation/submission intervals.

Control implementation and validation
-------------------------------------
The ignored renderer_control.cpp copies the current renderer.cpp and gates only
the added town setup/program switches behind a render-thread flag. Disabled,
town uses the original full basic program and omits the extra camera/lighting
setup and restoration binds. Enabled, it uses the implemented specialized path.
Both linked programs remain resident in both conditions; this is a draw-path
comparison, not a shader loading or allocation comparison.

The control compiles against the current Renderer header and normal Release
flags/libraries. Compiler dependencies and a linker map verify the matching
header and absence of the original renderer.cpp archive object. Production code
and its public API are unchanged by this diagnostic. Two unused standard-harness
helper warnings occur only in the scratch harness build.

Three standard views are retained: daytime town, flashlight town, and the sparse
old-forest 100 m view. Scene, tree and forest inputs, shader sources, cameras,
1280x720 resolution, reversed float32 camera depth, nearest vegetation filtering,
1024-square sun map and normal rendering policies match the preceding runs.
No AI, audio, player movement, dynamic physics or presentation runs. Animation
input follows the same deterministic 60 Hz sequence in every block.

Each block renders an untimed validation frame. Pixels must equal the first
condition in the same renderer, and source/draw counts must match. Captures from
both conditions in every process must also equal the frozen original benchmark
captures byte-for-byte. Scene/tree/forest draw counters are checked separately.
Warmups, checks, captures and CSV writing stay outside measured blocks.

Primary completed-frame protocol
--------------------------------
Four processes each retain one context/renderer for all three views. Every view
has eight blocks of 60 warmup and 512 measured frames. The base sequence is
original/town/town/original/town/original/original/town. Processes use this order,
its inverse, its inverse and this order, giving four adjacent pairs per process
and sixteen pairs per view.

After warmup and an untimed glFinish, elapsed CLOCK_MONOTONIC time brackets 512
render+glFlush calls and a final glFinish. That final retirement wait is included.
There are no per-frame CPU clocks, GPU timestamp queries, event polling or output
writes in primary blocks. Disabled probe checks remain common in the control
binary. Driver backpressure determines queue depth. This measures completed
offscreen render work, not presented FPS or latency.

For each process/view, pair adjacent blocks, calculate original-minus-town
milliseconds per frame, and take the median of four differences. The primary
aggregate is the median of four process medians. Percent uses the independently
aggregated original level as denominator. Flat original/town levels separately
take the median of four blocks per condition/process, then the median of four
processes. Their subtraction need not equal the paired estimate.

The rule was written before measurement: a clear gain requires >=1% paired
saving, positive medians in all four processes, and >=12 of 16 positive pairs.
Clear regression has symmetric negative conditions. Otherwise classification is
mixed. This is an operational threshold, not a significance or equivalence test.

Separate phase protocol
-----------------------
Two additional processes use the base and inverse orders, with 128 measured
frames per block and the same 60 warmups. Six timestamps bracket the whole
renderer, opaque town envelope and glass envelope. Query availability is checked
before reading results, with at most four frames in flight. CPU clocks measure
whole render, basic-program binds, extra town camera/lighting preparation,
visibility gathering, opaque submission and glass submission. Per-frame rows
are buffered and written after the timed block. Primary decisions do not use
phase-instrumented throughput.

Opaque GPU elapsed includes the candidate's extra preparation and restoration;
glass GPU elapsed includes its program/state changes. These are elapsed command
intervals, including driver/submission stalls, not isolated shader instruction
times. The extra CPU setup metric includes camera/lighting calculations and
uniform uploads; per-draw transform/material uniforms remain in submission time.
Program-bind timing covers all basic shader binds in the renderer. CPU/GPU
overlap, inclusive measurements and separately aggregated medians must not be
added together. Phase instrumentation can alter scheduling and clocks.

Interpretation and next work
----------------------------
This control supports keeping the first town variant: flashlight-town and the
sparse view satisfy the declared rule on both power sources, and daytime town
satisfies it on battery while remaining favorable/mixed on AC. The earlier
separate-process battery reversal does not repeat in this controlled comparison.
Do not promote the earlier 13% estimate to a universal daytime or gameplay gain.

The specialized path's flat completed-frame levels across power sources are
3.878 ms AC versus 4.052 ms battery in daytime town, 3.141 versus 3.123 ms for
flashlight town, and 5.998 versus 5.994 ms for the sparse view. These sessions do
not show a uniform power-source effect. Temperature, clocks and background work
remain uncontrolled, and this map-only case does not replace crowd/gameplay
power measurements.

Extra uniform preparation is only about 0.003 ms in town; eliminating it cannot
recover tenths of a millisecond by itself. Avoid a larger shader split or a
uniform-system rewrite based on this result. For further town optimization,
profile visibility gathering and opaque draw submission, each around 1 ms in
these diagnostics, then measure a focused culling/batching change and a matched
gameplay route. No production behavior was changed as part of this follow-up.
